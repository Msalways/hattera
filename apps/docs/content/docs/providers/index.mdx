Hattera starts supported agent CLIs on the computer running its server and presents their output in one app. Provider accounts and API keys determine access and billing.

## Built-in engines

| Engine | Authentication shape | Notes |
|---|---|---|
| Claude | In-app browser link and pasted authorization code | Strong support for tools, approvals, sessions, and local computer use |
| Codex | Codex CLI login | Model discovery, approvals, steering, and computer tools |
| Grok | Grok CLI login | ACP-based local model catalog and session support |
| Cursor | Cursor Agent CLI login or API key | ACP driver with live model discovery |
| Kimi | In-app browser link and one-time code | ACP integration |
| Droid | Factory API key entered in Settings | ACP integration |
| Cline | In-app browser link and one-time code, or compatible API credentials | ACP integration |
| Antigravity | Google account through the official ACP server | Managed install, isolated accounts, live models, and approval cards |
| OpenCode | Provider API keys in Settings; existing native accounts are retained | Live Zen, Go, third-party, and local model discovery through ACP |
| Qwen | Provider URL, model and API key in Settings | ACP integration |
| Hermes | Provider URL, model and API key in Settings | ACP integration |
| Pi | Provider URL, model and API key in Settings | Native driver |
| Amazon Bedrock | AWS region, model or inference profile ID, and Bedrock API key in Settings | Native Converse API; no CLI installation |

Additional driver instances can be declared in local configuration. Gemini CLI is available for enterprise and paid API-key deployments; consumer Google AI Pro, Ultra, and free-tier requests moved to Antigravity. An installed CLI is not proof of account access, and models appear only after Hattera can discover a usable route. Unavailable engines remain visible with a reason.

## Set up a hosted server from your browser

Open **Settings → Model providers and accounts**, expand an engine, and choose **Install on this server** if needed. Hattera installs it into its own tools directory as the server's user. Follow the sign-in link or enter the provider credentials in the same card. Cursor offers browser sign-in and an API-key alternative; optional Gemini CLI uses a Gemini API key. No server terminal is required for these built-in setup paths. Custom ACP commands still use the external provider's own setup process.

Installation and sign-in have separate states. An installed executable does not prove account access. A saved key is checked when the provider is used; model access and billing belong to the provider account. Existing native accounts remain usable, including accounts established with other vendor CLI login methods.

### Amazon Bedrock

Expand **Amazon Bedrock**, enter its **AWS region**, an enabled **model or inference profile ID**, and a **Bedrock API key**. Hattera uses the native Converse endpoint for text, images and tools. The selected ID is shown explicitly; Hattera does not invent an accessible AWS model catalog. Replies currently arrive as complete messages. This setup uses Bedrock API keys, not IAM access key pairs or automatic role credentials.

To use OpenRouter, Fireworks AI, DeepSeek, Cline, or your own OpenAI- or Anthropic-compatible service, see [Other model providers](./model-providers.mdx).

Codex models come from the signed-in CLI's live model list. If that list cannot be read, the picker shows an offline fallback that includes GPT-6 Astra, Sol, and Luna with availability marked unverified. An older CLI may not expose newer models; Hattera checks for a newer stable Codex release and offers an update command for the configured executable. Updating the CLI does not grant model access to an account.

## Mistral API

Open **Settings → Connections**, save your **Mistral API key**, then choose **Mistral (API)** in a bot's model picker. No CLI installation is needed. The **Test** button checks catalog access without sending a chat message.

The model list refreshes from Mistral's `/v1/models` endpoint, including versioned models and aliases. Archived and non-chat models are excluded. Use **Refresh models** after new models become available to your account; an unsuccessful refresh preserves the previous list. Mistral bills requests to your API account.

For a server deployment, set `MISTRAL_API_KEY` or save `mistral.key` in the server configuration. Advanced users can declare additional `mistral` instances with a `config.model` default and endpoint URL. A saved workspace key is shared by those instances. The connection supports streamed replies and structured tools through the shared chat-completions runtime; it does not launch a local agent CLI or grant filesystem access.

## Detection

Hattera checks common installation directories and the login shell in the background. After installing or authenticating a CLI, choose **Check again** in Model providers and accounts; no app restart is needed.

If detection fails, use **Settings → Model providers and accounts** to set an explicit executable path. This is supported for every engine and is the most reliable solution for version managers, wrappers, custom builds, and Windows installations outside the normal path.

## Model selection

The model picker groups models by provider and marks defaults. Supported engines can refresh their model catalog from the installed CLI. Changing the model affects future turns; it does not rewrite earlier transcript history.

## Codex browser tools

Codex bots use the browser and computer selected in Hattera. Desktop-only Codex
browser/computer features and their bundled plugins are disabled for those bot
processes, so bots do not select a native desktop connection that is unavailable
inside the CLI. This does not uninstall plugins or change the standalone Codex app.
Native web search keeps its configured mode.

After built-in browser navigation, Hattera collects a snapshot in the same
browser session. A sign-in page or redirect is evidence of where navigation landed,
not confirmation that the requested task finished. Connection failures retain the
selected computer/account and do not automatically replay uncertain actions.

## Multiple Claude accounts

Open **Settings → Engines → Add Claude account** and give the account a name, such as **Work** or **Personal**. Hattera creates a separate configuration-directory setting for it; it does not copy your existing login. Under **Manage account and sign-in**, start sign-in, open the browser link and paste the returned authorization code into Hattera. Claude stores its own credentials on the server.

In a bot's model picker, choose **Claude**, select **Work** or **Personal** in the **Account** dropdown, then choose a model to save the selection. Claude appears only once in the provider list. Each bot keeps its own selection, and the chat header shows the account name. Account changes apply to future turns and are blocked while that bot is responding; other bots are unaffected. Conversation history is not erased when you change the selection.

The original **Default** entry keeps using your existing CLI login. Advanced users can supply an existing, separate Claude configuration directory. Once an account has been used by bots or conversation history, add a new account instead of repointing its directory. Removing an account from Hattera does not delete its files or sign it out; first move any bots using it to another account.

This does not require a CLI proxy, and there is no automatic account rotation or fallback. Named account management currently supports Claude only.

<Callout type="info" title="Subscriptions stay with the provider">
  Your existing CLI login or provider API key determines access and billing. Hattera does not turn one subscription into access to another provider.
</Callout>
